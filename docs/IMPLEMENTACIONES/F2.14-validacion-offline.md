# F2.14 — Validación integral offline

## Resultado

Validación parcial con datos sintéticos. La captura y lectura persistente se verificaron manualmente sin conectividad tras terminar el proceso; las pruebas UI/Room de edición, historial y borrado pasaron también con el AVD sin red. El flujo manual de edición de la misma nota quedó bloqueado por un ANR de foco/entrada, así que no se declara completa la aceptación integral de F2.14.

## Dispositivo y protección de datos

- AVD `Medium_Phone_API_37.0`, `emulator-5554`, API 37. No había paquete YEZVI instalado antes de la sesión; se instaló el APK debug existente con `adb install -r`. No se usó `pm clear`, desinstalación ni reinicio del dispositivo.
- No había datos de YEZVI preexistentes que preservar en este AVD. Las pruebas instrumentadas usaron bases SQLite temporales con nombres únicos y entradas sintéticas; no tocaron la base principal.
- Antes de la prueba se deshabilitaron Wi‑Fi y datos móviles con `svc`; se confirmó `Active default network: none` y `ping 1.1.1.1` respondió `Network is unreachable` (modo avión permaneció apagado). Al terminar se reactivaron Wi‑Fi y datos móviles; el AVD volvió a tener red predeterminada validada.

## Flujo manual observado sin red

1. Se abrió YEZVI y se guardó desde Capturar el texto sintético `F214NoteOfflineSynthetic202610` (el campo limitó la entrada a 30 caracteres). La revisión mostró origen Texto, fecha 12 oct 2026, hora 10:29 y zona GMT; el mensaje de éxito indicó guardado local.
2. Memoria mostró la entrada persistida. Detalle mostró el texto original y los metadatos de captura (origen, fecha, hora, zona y guardado local).
3. `am force-stop` terminó el proceso (sin PID); al volver a iniciar la app, Memoria y Detalle recuperaron el mismo texto y metadatos. Esto verifica muerte forzada del proceso y reapertura, no un simple reinicio de Activity. No se reinició el AVD.
4. Al editar manualmente, la interacción de teclado/foco dejó de responder. `dumpsys activity lastanr` registró timeouts de `KeyEvent` (~10:32) y luego `FocusEvent(hasFocus=true)` (~10:34). La app se cerró desde el diálogo del sistema y se relanzó; no se guardó ninguna corrección en la nota. Por el ANR, no se completaron manualmente las dos correcciones ni el borrado de esta nota principal.

- `RoomMemoryRepositoryTest.consecutiveCorrectionsPreserveOriginalAndHistoryAfterReopen`: 1/1. Dos correcciones, original intacto e historial tras reabrir SQLite.

Con conectividad restaurada se ejecutó la suite completa solicitada: `assembleDebug` → BUILD SUCCESSFUL (tareas sin cambios, mayormente `UP-TO-DATE`); `testDebugUnitTest` → 28/28, 0 fallos; `connectedDebugAndroidTest` → 23/23, 0 fallos en API 37. No se ocultaron fallos ni se usaron reintentos de pruebas.

## Cierre y handoff

F2.14 tiene evidencia offline de captura/lectura tras muerte de proceso y de los flujos críticos mediante UI/Room instrumentados, pero la secuencia manual completa no se verificó por el ANR. El criterio del roadmap menciona Pixel 8: el AVD usado fue Medium Phone API 37, no Pixel 8; tampoco estuvieron disponibles API 24 ni Samsung físico. **Recomendación: no cerrar F2 aún**; reproducir y resolver/verificar el problema de foco en un Pixel 8 y completar manualmente dos correcciones, reapertura y borrado confirmado/cancelado. No se avanzó a F3.

No se modificó código, Gradle ni schemas. El schema v2 `2.json` permanece staged; no se hizo commit ni push. La nota sintética de la prueba manual queda en la base principal del AVD, sin datos personales ni limpieza destructiva.
