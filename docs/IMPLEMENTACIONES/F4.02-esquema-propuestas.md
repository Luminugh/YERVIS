## 1. Sobre común y versionado

Todos los objetos se cierran con `additionalProperties: false`. Las once variantes son `oneOf`, discriminadas por `category`; cada una referencia datos tipados. No hay bolsa arbitraria de campos, extensiones libres, herramientas ejecutables ni campos de aceptación/autoguardado.

| Campo obligatorio del sobre | Tipo / regla |
|---|---|
| schemaVersion | Constante exacta `1.0.0`. No convertir números, aceptar una versión “parecida” ni degradar una versión desconocida. |
| requestId | ID opaco creado por el host para la petición/consentimiento, no por la IA. Debe coincidir exactamente con la petición pendiente. |
| extractionId | ID opaco creado por el host para esa extracción de fuentes/versiones/configuración. Se conserva durante reintentos de transporte idénticos. Una petición distinta obtiene nuevo ID. |
| offsetUnit | Constante `UTF16_CODE_UNIT`, compartida por todos los rangos. |
| sourceSnapshots | De 1 a 16 descriptores de fuentes/versiones elegidas por el host; eco exacto, no autorización producida por IA. |
| outcome | COMPLETE: hay propuestas; PARTIAL: hay propuestas e incidencias; NO_PROPOSALS: cero propuestas y al menos una incidencia. COMPLETE describe salida del extractor, no aceptación o verdad. |
| proposals | De 0 a 32 propuestas; IDs únicos en esta extracción. |
| issues | De 0 a 16 incidencias tipadas. Permite declarar evidencia insuficiente/ambigüedad sin rellenar campos falsos. |

`requestId`, `extractionId`, `proposalId`, `occurrenceId`, `exceptionId` y referencias internas usan `[a-z][a-z0-9_-]{0,63}`. `proposalId` es **local a extractionId**, nunca un ID Room ni una identidad global de persona. La clave conceptual de propuesta es `(extractionId, proposalId)`; un ID generado por el modelo no basta para deduplicar reextracciones. F4.09 definirá la deduplicación semántica. La representación/creación de IDs de memoria existentes no cambia.

Cada propuesta requiere `proposalId`, `category`, `proposalStatus: "PROPOSED"` y `data`; `relations` es opcional. No existe campo de modificación directa del original. Relaciones UPDATES/CONTRADICTS son propuestas con evidencia y no instrucciones de escritura.

**Estados y autoridad:** la respuesta IA solo admite PROPOSED. El host podrá registrar posteriormente aceptación, rechazo, sustitución o expiración con actor y fecha; el modelo no puede fabricar esos estados o auditoría. F4.06 implementará el ciclo local. `data.state` describe la actividad (por ejemplo COMPLETED), no el estado de revisión. Confirmación explícita reportada en una nota sigue siendo una afirmación con fuente, no aceptación en la app. Guardar la nota original tampoco acepta su extracción.

Versiones futuras requieren un nuevo identificador y artefacto de schema, con lista local explícita de versiones soportadas y pruebas. El artefacto 1.0.0 queda como referencia inmutable una vez adoptado; no añadir silenciosamente un enum/campo al archivo que consume un cliente antiguo. En este directorio, una futura revisión menor usará otro archivo identificado, por ejemplo `proposals-1.1.0.schema.json`; una mayor usará otro directorio. Sin negociador, migración de propuestas o compatibilidad automática en F4.02. Versión desconocida: rechazar lote, preservar original y pedir extracción compatible, sin acciones parciales.

## 2. Fuente, revisión y evidencia por campo

Un snapshot contiene `sourceEntryId` (cadena opaca no vacía, hasta 128 caracteres), `revision`, `sourceType` (TEXT/VOICE existente), `capturedAtEpochMillis`, `timezoneId`, `textSha256`, `textLengthUtf16` y `authorizedRanges` (1–8 intervalos). La identidad de snapshot es `(sourceEntryId, revision)`, no solo entryId. Se pueden comparar revisiones del mismo recuerdo, pero no cuentan como observaciones independientes de una rutina. sourceType se coteja con el host, sin inventar MIXED ni resolver el pendiente de origen mixto.

- Original: `revision: {"kind":"ORIGINAL"}`. Corrección: `{"kind":"CORRECTION","correctionId":"7"}`; se usa el correctionId existente, sin inventar un contador de revisión.
- `capturedAtEpochMillis` conserva el UTC original en **milisegundos**. En este nuevo transporte es una cadena decimal canónica con signo opcional, sin `+`, ceros iniciales ni exponentes, para preservar Long sin redondeos JavaScript. correctionId es cadena decimal positiva. F4.04 debe comprobar límites Long; regex/longitud no bastan. Ningún contrato Kotlin/Room se convierte a String.
- `textSha256` es SHA-256 del texto **completo de esa revisión**, codificado UTF-8 sin BOM ni normalización. `textLengthUtf16` mide unidades UTF-16. Ambos los calcula el host y la IA los repite sin cambiarlos. Hash/eco no son firma ni evidencia de consentimiento.
- El host conserva texto/versiones y rangos autorizados para cotejo. En un envío futuro solo prepara fragmentos consentidos con offsets absolutos, no el historial ni el texto completo por obligación del schema. Que el host conozca un snapshot no autoriza a enviarlo.

Cada campo semántico usa este wrapper; se omite si no hay soporte:

```json
{
  "value": "COMPLETED",
  "evidence": [{
    "sourceEntryId": "s-completed",
    "revision": {"kind": "ORIGINAL"},
    "quote": "Ya terminé el informe",
    "range": {"startUtf16": 0, "endUtf16": 21}
  }],
  "assessment": {
    "basis": "EXPLICIT", "modality": "ASSERTED", "polarity": "AFFIRMED",
    "certaintyValidation": "UNVALIDATED"
  }
}
```

El ejemplo coincide con la revisión sintética `Ya terminé el informe.`. Evidencia admite 1–8 fuentes/fragmentos por campo. Un título resumido puede normalizar texto sin inventar significado; la **cita** debe ser literal. Para valores compuestos, los contenedores (`temporal`, `recurrence`, `attribution`, etc.) organizan hojas semánticas con wrappers; no se atribuye una única certeza global a toda una persona o rutina. Metadatos de protocolo (IDs, categoría, discriminadores, precisión/incertidumbre de resolución) no son afirmaciones extraídas y se validan contra sus campos sustentados y el contexto del host.

Rangos: cero inicial, inicio inclusivo y fin exclusivo `[startUtf16,endUtf16)`, sobre la revisión completa exacta, antes de recortar para envío. Sin trim, lowercasing ni NFC/NFD. CRLF cuenta dos unidades y un emoji fuera de BMP cuenta dos. No se permite cortar un par sustituto; `substring(start,end)` de Kotlin debe coincidir con quote y el intervalo debe quedar entero en una ventana autorizada. No “arreglar” un offset buscando otra coincidencia: dos frases iguales pueden referirse a acontecimientos distintos. Si el emisor cuenta puntos Unicode/bytes, rechazar su evidencia y solicitar salida correcta.

`data.title.assessment` expresa el alcance de la afirmación principal. Una fecha u otro campo no puede convertir un título negado/hipotético en cita activa. La polaridad/modalidad de cada campo conserva su propio alcance; dos cláusulas opuestas pueden producir dos propuestas relacionadas en vez de perder la negación.

## 3. Fundamento, modalidad, negación y certeza

| Propiedad de assessment | Valores / efecto |
|---|---|
| basis | EXPLICIT o INFERRED. Normalizar “terminé” a COMPLETED puede ser explícito; añadir una conclusión que requiere varias notas es inferencia. |
| modality | ASSERTED, DESIRED, POSSIBLE, CONDITIONAL, UNCERTAIN, QUESTION. Una intención no acredita ejecución; una pregunta no acredita evento. |
| polarity | AFFIRMED o NEGATED; conservar alcance de la cita. Cancelación y finalización se expresan además como estado de actividad cuando constan. |
| certaintyValidation | Solo UNVALIDATED en una respuesta IA. La IA no puede emitir certeza validada/calibrada por sí misma. |
| inferenceExplanation | Obligatoria si basis=INFERRED, hasta 512 caracteres. Debe explicar vínculo entre fuentes y conclusión, sin servir como evidencia de sí misma. |
| technicalScore | Opcional: value numérico finito acotado, scale=LOGIT/LOG_PROBABILITY/UNNORMALIZED_MODEL_SCORE y methodId. Solo diagnóstico técnico con método verificable, no probabilidad de acierto, verdad o permiso. No se requiere ni se muestra en el editor. |

No se inventan scores en fixtures ni métricas reales de un modelo. F4.04 rechazará scores de métodos no verificables en el contexto o los excluirá de uso sin tratarlos como certeza. Una calibración validada sería metadato local separado con procedencia/dataset/método; queda fuera de este schema y del mapa experimental STT.

## 4. Datos tipados de las once categorías

`title` es obligatorio y tiene evidencia en todas las categorías. Los campos no listados para su categoría están prohibidos. Los opcionales se omiten, **no se rellenan con null, listas vacías, false, UNKNOWN o cero por defecto**. UNKNOWN solo se usa si existe evidencia que justifica expresar desconocimiento. El único null permitido es `temporal.resolved: null`.

| Categoría | Obligatorios adicionales | Campos opcionales con soporte |
|---|---|---|
| TASK | — | state, actor, project, dueAt, plannedAt, durationSeconds, priority, dependsOn, location, recurrence |
| EVENT | — | state, participants, project, startsAt, endsAt, durationSeconds, location, recurrence |
| ROUTINE | patternKind | person, recurrence, observedPeriod, occurrences, exceptions, trackingIntent; observado exige periodo y ocurrencias |
| HABIT | — | person, desiredFrequency, trackingIntent, occurrences, exceptions, goal |
| REMINDER | target, request, trigger | Sin enabled, execute, schedule, canal operativo o permiso de notificación |
| IDEA | — | themes, resources, project |
| FACT | factKind, attribution | subject, project, scope, occurredAt, observedPeriod; condiciones especiales abajo |
| DECISION | — | actor, project, decidedAt, reasons, alternatives |
| GOAL | — | actor, project, targetAt, successCriteria, progress |
| PERSON | — | aliases, context; no diccionario de rasgos permanentes o puntuación psicológica |
| PROJECT | — | state, participants, targetAt, goal |

TASK.state: PENDING/IN_PROGRESS/COMPLETED/CANCELLED/BLOCKED/POSTPONED/UNKNOWN. EVENT.state: TENTATIVE/SCHEDULED/HELD/CANCELLED/POSTPONED/UNKNOWN. PROJECT.state: PROPOSED/ACTIVE/PAUSED/COMPLETED/CANCELLED/UNKNOWN. Son estados reportados y revisables, no hechos confirmados por el sistema. Duraciones son segundos enteros positivos hasta 31.536.000, solo si expresadas o normalizables con evidencia; no adivinar duración por “reunión”. Prioridad LOW/NORMAL/HIGH/URGENT requiere evidencia, sin completar NORMAL por defecto.

FACT.factKind: OCCURRENCE, ASSERTION, PREFERENCE, PERSONALITY_DESCRIPTION, BEHAVIOR_OBSERVATION, BOUNDED_CONCLUSION o RELATIONSHIP_ASSERTION. `attribution.kind` distingue CAPTURE_AUTHOR, REPORTED_PERSON (speaker referenciado) y MODEL_CONCLUSION. Una preferencia o descripción de personalidad se vincula al sujeto y a quien la afirma; no acredita causalidad, diagnóstico, confiabilidad o rasgo estable.

PERSONALITY_DESCRIPTION y BOUNDED_CONCLUSION requieren subject y scope. BOUNDED_CONCLUSION también requiere observedPeriod, atribución MODEL_CONCLUSION y título con al menos dos evidencias, basis=INFERRED y modality=UNCERTAIN. F4.04 comprobará independencia de fuentes y que la conclusión no excede el periodo/contexto observado. Dos citas no prueban automáticamente un patrón. Preferencias/rasgos/relaciones se representan como FACT atribuibles enlazados a PERSON; PERSON no agrega un perfil permanente ni crea ficha por cada mención.

## 5. Fechas, recurrencia y seguimiento

`temporal` requiere `expression` con evidencia, `anchor` (sourceEntryId+revision), `precision`, `uncertainty` y `resolved`. El snapshot de anchor proporciona instante/zona de captura para F4.05. La expresión literal nunca se sustituye por una fecha calculada.

- precision: UNSPECIFIED, DAY, PART_OF_DAY, MINUTE o SECOND. uncertainty: UNRESOLVED, AMBIGUOUS, APPROXIMATE o NONE_REPORTED; no son probabilidades. No asignar precisión superior a la evidencia.
- resolved=null cuando no se resolvió. Si hay resolución, es objeto no vacío con localDate (`YYYY-MM-DD` real), localTime (`HH:mm` o `HH:mm:ss`, 00–23), timezoneId IANA y/o instantEpochMillis decimal en milisegundos. Cada componente resuelto lleva evidencia y assessment; su cálculo necesita justificación si inferido. Si hay instante, fecha/hora/zona son obligatorias y deben ser coherentes. Fecha sola no implica medianoche ni un instante.
- El schema solo comprueba forma de zona; Kotlin debe consultar IANA/ZoneId y tratar ambigüedad DST. No aceptar automáticamente una cadena que parece zona. Si el host rechaza un ID o época fuera de sus capacidades, preservar el original y señalar el límite, sin convertir unidades o cambiar metadatos.
- Roles se distinguen por posición: EVENT.startsAt/endsAt, TASK.dueAt/plannedAt, REMINDER.trigger.at, FACT.occurredAt, DECISION.decidedAt y GOAL/PROJECT.targetAt. No usar capturedAt como fecha del hecho o del evento. `period.from/to` son extremos descriptivos inclusivos según precisión, no un intervalo ejecutable de alarmas; no inventar extremos si solo se menciona uno.

`recurrence` requiere frequency con evidencia (DAILY/WEEKLY/MONTHLY/YEARLY/FLEXIBLE). Opcionales: interval (1–366 unidades de frequency), weekdays (MO…SU), monthDays (1–31), months (1–12), times (hasta cuatro horas), window, timesPerPeriod (1–366), timezoneId y validity. WEEKLY admite weekdays; MONTHLY monthDays; YEARLY months+monthDays. DAILY excluye esos filtros; FLEXIBLE excluye filtros de calendario, interval y timesPerPeriod porque no define su periodo. No hay semántica implícita de “primer lunes del mes”.

interval ausente no inventa una frecuencia más precisa; no ejecutar recurrencia sin completar/confirmar las reglas necesarias. Un ciclo de varias semanas necesita origen de ciclo sustentado (por ejemplo validity.from explícito); no usar captura como ancla del calendario sin evidencia. FLEXIBLE describe frecuencia no fijada, no un calendario generado. Calendarios especiales, “último día hábil”, cron o RRULE arbitrario no se inventan: conservar expresión en title/temporal y emitir NEEDS_CLARIFICATION/UNSUPPORTED_CONTENT; una futura versión tipará lo necesario.

ROUTINE.patternKind=DECLARED exige basis EXPLICIT. OBSERVED exige basis INFERRED, al menos dos evidencias, periodo y al menos dos ocurrencias; **el mínimo estructural no es umbral estadístico suficiente**. Deben ser ocurrencias/fuentes independientes en días pertinentes, sin contar dos revisiones o duplicados como dos hechos. No se promete continuidad semanal por observar tres lunes.

Ocurrencia: occurrenceId local, at temporal y state con evidencia; linkedProposal opcional. Estados: COMPLETED, SKIPPED_EXPLICITLY, POSTPONED, CANCELLED o UNKNOWN. La ausencia de notas no permite generar SKIPPED_EXPLICITLY ni “incumplida”. Excepción: exceptionId, period, effect y description; replacementRecurrence opcional. effect: PAUSED/CANCELLED_OCCURRENCE/RESCHEDULED/FREQUENCY_CHANGE. Una excepción afecta su periodo/ocurrencia, no borra la plantilla.

HABIT.desiredFrequency expresa lo que se desea, no práctica demostrada. `trackingIntent` solo refleja REQUESTED/DECLINED con evidencia; ausencia no autoriza seguimiento, telemetría ni notificación. No existe flag operativo para habilitarlos.

## 6. Relaciones y recordatorios sin autoridad de ejecución

Un refField contiene `value: {"proposalId":"ana"}` con evidencia/assessment. Solo referencia propuestas **de la misma extracción**; no se aceptan IDs Room/entidades previas arbitrarios en v1. Las menciones quedan sin resolver a identidad global hasta revisión; homónimos no se fusionan. Un contexto ambiguo puede omitir la referencia y emitir incidencia. No crear una PERSON ficticia para completar actor.

Kotlin deberá verificar destinos: actor/person/participants/speaker → PERSON; project → PROJECT; goal → GOAL; dependsOn → TASK; progress → TASK o FACT; subject → PERSON o PROJECT en v1; linkedProposal → TASK/EVENT/FACT. Para otra asociación usar RELATED_TO respaldado, sin forzar un sujeto de tipo ajeno. REMINDER.target → TASK/EVENT/ROUTINE/HABIT/FACT/GOAL sustentado. No referencia a sí mismo, ciclos de dependencia o borrados arbitrarios. Las referencias forward dentro del lote son válidas si terminan resolviéndose.

`relations` usa un wrapper por relación: `{kind:CONTRADICTS|UPDATES|SUPPORTS|RELATED_TO,targetProposalId}`. Evidencia puede unir varias fuentes. UPDATES y CONTRADICTS deben mantener categoría compatible y un enlace inequívoco; no trasladar revisión/aceptación automáticamente. La contradicción permanece visible y origina incidencia, no “gana” por ser más reciente. Para comparar con información anterior, un futuro host puede preparar sus **fuentes autorizadas** en esta extracción; v1 no concede acceso libre a toda la base ni sobrescribe registros derivados anteriores.

REMINDER requiere request=REQUESTED respaldado por petición explícita, target y trigger. Tipos de trigger: AT(at), BEFORE(relativeTo+secondsBefore), CONDITION(condition literal). relativeTo: EVENT_START/EVENT_END/TASK_DUE/TASK_PLANNED/ROUTINE_OCCURRENCE. BEFORE se verifica contra categoría/fecha destino; condición no implementada se queda pendiente. Un target o momento ambiguo no programa nada. La autorización de F8 será otra acción explícita del usuario, fuera de la extracción y posterior a su revisión. Una petición inferida no se trata como REQUESTED.

## 7. Límites, nulabilidad y errores

| Límite v1 | Valor |
|---|---|
| Respuesta UTF-8 / profundidad | Máximo 262.144 bytes / 32 niveles; comprobar antes/durante parsing |
| Fuentes | 1–16; cada revisión hasta 8.192 unidades UTF-16; suma de texto autorizado hasta 32.768 unidades |
| Ventanas por snapshot | 1–8, dentro de la revisión; no solapadas ni invertidas |
| Propuestas / incidencias | Hasta 32 / 16; sin truncar silenciosamente |
| Evidencias por campo / totales | 1–8 / máximo 1.024 referencias de evidencia en la respuesta |
| Cita / texto de campo | Hasta 1.024 puntos Unicode por schema; cadenas cortas hasta 256; rechazar blanco sin normalizar la fuente |
| Relaciones / participantes | Hasta 16 por colección; dependencias y alternativas/razones hasta 8 |
| Ocurrencias / excepciones | Hasta 16 / 8 por rutina/hábito; no expandir todo un calendario |
| IDs / enteros | IDs locales hasta 64; entryId hasta 128; Long decimal canónico con comprobación exacta posterior |
| Valores ausentes | Omitir opcionales; `null` solo temporal.resolved; sin campos adicionales ni categorías/estados desconocidos |

JSON Schema cuenta longitud de strings por caracteres Unicode; los offsets son unidades UTF-16 deliberadamente distintas. Los límites de bytes, profundidad, suma, unicidad por valor y cotas Long son de parsing/validación local, no garantizados por regex. Una fuente que exceda el presupuesto no se recorta/reindexa sin rehacer contexto autorizado y consentimiento; el original no cambia.

Solo JSON UTF-8 válido sin BOM, comentarios, texto alrededor, claves duplicadas, NaN/Infinity o números exponenciales para IDs/épocas. No coerción de tipos. Rechazar la respuesta incompatible sin guardar propuestas ni activar acciones; permitir revisión/reextracción compatible. Transporte, cuota o proveedor ausente se manejan fuera del sobre y nunca pierden la captura local. LIMIT_REACHED/PARTIAL puede proponer dividir la extracción de forma explícita, sin continuar envíos automáticamente.

## 9. Puertas que deberá implementar F4.04 (y resolución F4.05)

1. Parsing estricto/presupuesto: bytes, profundidad, claves duplicadas, números/Unicode válidos y cotas de colecciones antes de evaluar; versión exacta y refs de Schema exclusivamente locales. Nada de resolver `$ref` o URLs de una respuesta en red.
2. Correlación y autorización: cotejar requestId/extractionId, fuente+revisión, hash, captura, zona y rangos contra el contexto local inmutable autorizado. IDs inexistentes, revisiones cambiadas o snippets no consentidos invalidan evidencia; un eco del modelo no crea permisos.
3. Citas y offsets: igualdad literal, start<end, límites y pares sustitutos, ventanas autorizadas, índice absoluto en revisión correcta. Comprobar cada campo y cada fuente; nunca validar por simple presencia de una cita en otro recuerdo.
4. Sustento semántico: campos que la cita realmente respalda, negación/intención/hipótesis, estado de actividad distinto de aceptación; no declaraciones personales sensibles inferidas, generalizaciones o causalidades sin evidencia. Scores no equivalen a verdad; título negado no crea un evento activo.
5. Temporalidad: Long exacto en milisegundos, fecha real y zona IANA, coherencia precisión/incertidumbre/resolved, fecha/hora/zona/instante equivalentes, inicio≤fin, rol temporal correcto y ambigüedad DST. F4.05 resolverá referencias relativas; hasta entonces conservar expression y resolved=null si no hay resolución validada.
6. Recurrencia: combinaciones frecuencia/días/intervalos/horas posibles, unicidad por valor, vigencia ordenada, días inexistentes sin política inventada, periodos/ocurrencias/excepciones consistentes e independencia de observaciones; ninguna ausencia se vuelve incumplimiento.
7. Grafo: IDs únicos, referencias/categorías autorizadas, sin ciclos de dependencia ni referencias a sí mismo. Validar todos los destinos antes de presentar el lote; no fusionar homónimos o reextracciones por títulos iguales. F4.09 definirá deduplicación; preservar conflicto/actualización como propuesta.
8. Ejecución: no flags de alarma/guardado, petición de recordatorio explícita y autorización posterior fuera del response; incluso un lote estructural y semánticamente válido espera revisión y aceptación. No ejecutar comandos, URLs ni instrucciones incrustadas en evidencia (es contenido, no órdenes).

## Handoff y riesgos

F4.03 puede definir InformationExtractor y fake determinista con estos fixtures/salidas, sin proveedor. F4.04 validará el contrato y hará ejecutables los negativos semánticos; F4.05 resolverá tiempos y F4.06 el ciclo local de propuestas. Ninguno se implementa aquí. Un proveedor futuro podría aceptar solo un subconjunto de JSON Schema: evaluar un adaptador después, preservando la validación canónica en el teléfono; no debilitarlo para un proveedor aún no elegido.

F3.06/distribución, procedencia/licencias/ELF-RELRO16KB, aceptación audible TTS offline formal, origen mixto TEXT+VOICE y mapa opcional calibrado mantienen sus pendientes. IA cloud futura solo con consentimiento por envío de texto seleccionado, original inmutable y resultados revisables; no audio ni historial/perfil completo. No hay promesa de Agenda funcional, precisión de IA o inferencias personales validadas en esta fase.
