# F2.09 — Edición segura de recuerdos

## Estado

Implementada con migración aprobada v1→v2. El texto capturado y sus metadatos permanecen en `memory_entries` como fuente inmutable; cada corrección explícita crea una fila nueva en `memory_entry_corrections`.

## Contrato y almacenamiento

`MemoryCorrectionRepository` expone `addCorrection`, `getCurrentVersion` y `getCorrectionHistory` sin depender de Room. `MemoryTextVersion.correctionId == null` identifica el texto original vigente; un ID y `modifiedAtEpochMillis` presentes identifican una corrección. El historial se consulta en orden ascendente de `correctionId`, que define el orden de inserción incluso si el reloj retrocede o dos cambios comparten milisegundo.

La entidad v2 tiene estas columnas `NOT NULL`:

| Columna | SQLite | Regla |
|---|---|---|
| `correctionId` | `INTEGER` | PK autogenerada `AUTOINCREMENT` |
| `memoryEntryId` | `TEXT` | FK a `memory_entries.id`; índice compuesto con `correctionId` |
| `correctedText` | `TEXT` | Texto literal no vacío |
| `modifiedAtEpochMillis` | `INTEGER` | Instante UTC en milisegundos |

El DAO solo permite insertar y consultar revisiones; no expone `UPDATE` ni borrado de correcciones. La FK usa `ON DELETE CASCADE` para que un futuro borrado explícito del recuerdo no deje historial huérfano. Ese flujo de borrado no se implementa en F2.09.

Para cerrar la vía de mutación anterior, se retiró `update(MemoryEntry)` de `MemoryRepository` y `@Update` de `MemoryEntryDao`; ya no hay operación genérica que pueda reescribir `rawText`, ID, origen, instante o zona. Las correcciones se guardan solo mediante el contrato append-only. `DemoMemoryRepository` y las pantallas no se modificaron.

## Migración y schema

`YezviDatabase` sube de v1 a v2 y `YezviDatabaseFactory` registra `MIGRATION_1_2`, implementada como migración Room suspendida sobre `SQLiteConnection`. Solo crea la tabla y su índice. No copia, actualiza ni elimina filas; no hay backfill ni `fallbackToDestructiveMigration`.

Se conserva sin cambios `app/schemas/com.yezvi.assistant.data.local.memory.YezviDatabase/1.json`. KSP2 exportó `app/schemas/com.yezvi.assistant.data.local.memory.YezviDatabase/2.json`, incluyendo FK, índice, tipos, PK autogenerada y restricciones. La apertura de la base migrada por Room verifica el schema nuevo.

## Pruebas y validación

`MemoryCorrectionMigrationTest` crea en archivo SQLite la estructura v1 exacta de `1.json`, su `user_version` e `identity_hash`, inserta una fila sintética y abre con la factory de producción. Comprueba migración real, preservación exacta de `rawText`/origen/instante/zona/ID, versión original sin revisiones, dos correcciones append-only, última versión por ID creciente (aunque el timestamp sea anterior), rechazo FK sin huérfanos y persistencia de original/historial tras cerrar y reabrir.

Un segundo caso introduce una vista sintética que bloquea la creación del índice y fuerza un error dentro de la migración. Tras el fallo verifica `user_version = 1`, fila original intacta y ausencia de tabla parcial. La prueba no usa datos personales.

Se evaluó `MigrationTestHelper` de Room 3, pero no se añadió: el artefacto 3.0.3 necesita kotlinx.serialization 1.8.1 para leer schemas y la resolución consistente actual de la app fija 1.7.3; en el AVD, el helper lanzaba `AbstractMethodError` antes de ejecutar la migración. El fixture de v1 usa el DDL/hash comprobados del snapshot versionado y deja que la factory y la validación de schema de Room realicen la migración. No cambia dependencias de test; `androidx.sqlite:sqlite-async:2.7.1` se declara para compilar el `executeSQL` suspendido oficial sobre `SQLiteConnection`.

## Referencia

Se siguió la API oficial de [migraciones Room](https://developer.android.com/training/data-storage/room/migrating-db-versions): las migraciones Room 3 reciben `SQLiteConnection` y son suspendidas. El schema de producción se genera con Room Gradle Plugin/KSP, no se edita a mano.

## Handoff

F2.09 queda implementada. F2.10 puede agregar borrado explícito del recuerdo, respetando la cascada del historial y solicitando confirmación desde su futura UI. F2.11 podrá consumir `MemoryCorrectionRepository` para editar; no iniciar automáticamente.
