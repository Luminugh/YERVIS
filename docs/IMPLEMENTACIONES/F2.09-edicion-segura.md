# F2.09 — Edición segura de recuerdos

## Estado: propuesta de esquema v2 pendiente de aprobación

F2.09 no puede persistir correcciones respetando el contrato actual sin ampliar el esquema: `memory_entries.rawText` es la captura original y v1 no tiene campos de corrección. Modificar esa columna destruiría la fuente. Por la instrucción de no ejecutar una migración sin aprobación, este documento propone primero el cambio; no se alteró código, schema JSON, Entity, DAO, repositorio, versión de base ni dependencias.

## Propuesta mínima: tabla append-only de correcciones

Mantener `memory_entries` intacta y agregar `memory_entry_corrections` en v2. Una fila representa una revisión explícita y conserva las versiones anteriores:

| Columna | SQLite | Restricción | Uso |
|---|---|---|---|
| `correctionId` | `INTEGER NOT NULL` | PK autogenerada de la revisión | ID estable y creciente; no sustituye el ID del recuerdo. |
| `memoryEntryId` | `TEXT NOT NULL` | FK → `memory_entries(id)` | Vínculo al recuerdo original. Índice por padre e ID de revisión. |
| `correctedText` | `TEXT NOT NULL` | No vacío validado antes de insertar | Texto corregido literal de esta revisión. |
| `modifiedAtEpochMillis` | `INTEGER NOT NULL` | UTC Unix epoch en milisegundos | Instante de guardado de esta revisión; no cambia `capturedAtEpochMillis`. |

SQL propuesto:

```sql
CREATE TABLE IF NOT EXISTS `memory_entry_corrections` (
  `correctionId` INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  `memoryEntryId` TEXT NOT NULL,
  `correctedText` TEXT NOT NULL,
  `modifiedAtEpochMillis` INTEGER NOT NULL,
  FOREIGN KEY(`memoryEntryId`) REFERENCES `memory_entries`(`id`) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS `index_memory_entry_corrections_memoryEntryId_correctionId`
  ON `memory_entry_corrections` (`memoryEntryId`, `correctionId`);
```

La revisión actual se obtiene por `correctionId DESC` filtrando `memoryEntryId`; el ID autogenerado conserva el orden de inserción aunque el reloj retroceda o dos ediciones compartan milisegundo. `modifiedAtEpochMillis` conserva el instante UTC de cada revisión. Si no hay revisiones, la presentación usa `rawText`. Cada guardado exitoso agrega una revisión; nunca actualiza `rawText` ni reescribe origen, instante, zona o ID del registro. El cascade elimina solo revisiones ligadas al padre si F2.10 elimina ese recuerdo; no se implementa borrado aquí. El historial contiene el original v1 más las revisiones guardadas, no borradores UI.

## Migración aditiva v1 → v2 propuesta

1. Conservar sin cambios `app/schemas/com.yezvi.assistant.data.local.memory.YezviDatabase/1.json`; subir `YezviDatabase.version` a 2 y exportar `2.json` mediante Room 3.0.3/KSP2.
2. Registrar una migración Room `1→2` que únicamente cree la tabla, la FK y el índice anteriores con APIs `androidx.room3`/`SQLiteConnection`.
3. No copiar, renombrar ni actualizar filas existentes: cada entrada v1 sobrevive byte por byte en sus columnas. La tabla queda inicialmente vacía y las lecturas muestran el original hasta que el usuario confirme una corrección.
4. No habilitar `fallbackToDestructiveMigration`, borrar snapshots ni ejecutar `clearAllTables`. Si la migración o escritura falla, propagar el error y conservar la base anterior.

- Añadir Entity/DAO para correcciones sin modificar las columnas de `MemoryEntryEntity`; verificar que la consulta y operación de corrección siempre reciben `memoryEntryId` y no pueden cambiar otra entrada.
- Exponer un contrato/repositorio acotado para añadir corrección, recuperar original y observar historial o corrección más reciente. Una transacción comprobará que existe el padre antes de insertar; ID padre inexistente debe producir resultado/error honesto y ninguna fila huérfana.

Añadir dos correcciones; verificar historial ordenado, selección determinista de la última, recuperación intacta de `rawText`, metadatos intactos, errores/rollback y persistencia tras cerrar/reabrir SQLite.
- Usar dependencias ya presentes cuando sea posible; `room3-testing` no está declarado actualmente y solo se propondrá si es necesario para validar la migración real.
- Sin UI de edición (F2.11), borrado (F2.10), voz ni IA. No se añaden dependencias ni pruebas de código antes de aprobar el esquema.
