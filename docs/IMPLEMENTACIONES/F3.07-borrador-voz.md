# F3.07 — Borrador editable desde STT

**Estado:** lógica de presentación implementada; sin conexión a la UI. F3.06 permanece abierta por la aceptación de micrófono humano y la revisión de distribución.

## Alcance y límites

Se revisaron los contratos F1/F2, `SpeechToTextEngine`, `VoiceCaptureSessionController`, `SherpaOfflineSpeechToTextEngine`, `CaptureViewModel` y `CaptureScreen`. El controlador y el guardado textual ya existían, pero Capturar todavía no transportaba un resultado STT a un borrador.

Se añadió [VoiceTranscriptDraftCoordinator](../../app/src/main/java/com/yezvi/assistant/presentation/capture/VoiceTranscriptDraftCoordinator.kt) en `presentation/capture`. Recibe una sesión del controlador existente y usa `CaptureViewModel` para guardar tras aceptación. No se cambió `CaptureScreen`, `CaptureViewModel`, el contrato STT, Room, los permisos, Gradle ni los motores. Tampoco se conectó una ruta de audio a la interfaz: eso queda para F3.08/F3.09.

## Contrato del borrador

- `VoiceDraftSession` fija un ID de sesión, el instante UTC en milisegundos y la zona horaria al iniciar. El ID de memoria se genera después por el `CaptureViewModel` existente y se conserva al reintentar.
- `VoiceTranscriptDraft.recognizedText` conserva exactamente el texto final recibido. `editableText` empieza idéntico y puede cambiar independientemente; no se corrigen nombres, números, puntuación, mayúsculas ni espacios automáticamente.
- Un resultado no escribe en Room. Sin texto de captura previo, el estado pasa a `Candidate`. Si hay borrador textual, pasa a `AwaitingTextDraftDecision`; el llamador debe elegir `REPLACE_WITH_VOICE`, `APPEND_VOICE` o `KEEP_EXISTING`. El coordinador no muta el borrador textual externo. Anexar agrega un salto de línea solo cuando el texto existente no termina ya en espacio en blanco.
- `accept()` construye `CaptureInput` con el `editableText` exacto, `CaptureSourceType.VOICE`, el instante y zona de sesión, y llama a `CaptureViewModel.save`. `Saved` solo se emite al observar la entrada persistida. El texto guardado es la versión que el usuario aceptó; `recognizedText` queda disponible en el estado de revisión, no se duplica como columna persistente.
- `SaveFailed` retiene el borrador y el ID generado; `retrySave()` reutiliza `CaptureViewModel.retry()`. Aceptaciones repetidas no crean una segunda operación; texto en blanco, descarte, cancelación, error STT y resultado tardío no generan guardados.
- El cierre invalida la sesión pendiente y delega en `VoiceCaptureSessionController.close()` para cancelar y liberar el motor.

## Anotaciones experimentales

Las anotaciones opcionales solo contienen rangos UTF-16 internos y empiezan vacías. No se leen scores Sherpa, no representan probabilidad ni se generan avisos. Rangos inválidos se descartan sin cambiar el texto. Cualquier edición distinta descarta los rangos previos; el modelo sigue funcionando sin ellos. [D-013](../DECISIONES.md#d-013--incertidumbre-stt-experimental-y-separada-del-producto-f306) y el [prototipo F3.06 debug](F3.06-prototipo-confianza.md) permanecen intactos y separados.

## Pruebas

`VoiceTranscriptDraftCoordinatorTest` usa un motor y repositorio falsos deterministas, sin micrófono, Android audio ni red. Sus 8 casos cubren literalidad, edición separada, rangos inválidos, borrador previo y sus tres decisiones, aceptación con metadatos, fallo/reintento con ID estable, descarte y resultado tardío, sesiones consecutivas, resultado vacío y error. También confirma que aceptar de nuevo tras completar no duplica el guardado. No se añadieron instrumentadas: no hubo UI ni APIs Android que requirieran una prueba de dispositivo.

Validación final:

- `:app:assembleDebug` — correcto.
- `:app:testDebugUnitTest` — **173/173**, 0 fallos, 0 errores; prueba focalizada **8/8**.
- `:app:assembleRelease` — correcto; `verifyReleaseSpeechIsolation` pasó y el APK release no incorpora el runtime/diagnóstico debug.
- No se ejecutó `connectedDebugAndroidTest` ni validación visual: no hay integración Compose en esta fase.

El primer intento de build encontró un import faltante y las primeras pruebas focalizadas detectaron sincronización incorrecta en las aserciones de aceptación; ambos se corrigieron y las tareas anteriores corresponden a la repetición final aprobada.

## Handoff F3.08/F3.09

F3.08 puede crear el controlador y coordinador con el ciclo de vida de Capturar, recoger `state` de forma lifecycle-aware y ofrecer inicio, parada y cancelación según `Recognizing.speechState`; no debe presentar aún el resultado como guardado. F3.09 puede editar `Candidate.draft.editableText`, resolver el conflicto textual explícitamente, llamar a `accept()`/`retrySave()` y descartar con `discard()`. Al salir debe llamar a `close()`.

Riesgos pendientes: estas clases aún no se instancian desde `YezviApp`/`CaptureScreen`; la lógica de selección de texto requiere presentarse en F3.09. La procedencia del texto anexado se registra como `VOICE` porque `CaptureSourceType` no contempla origen mixto; confirmar esa semántica antes de exponer “Anexar” al usuario. F3.06 sigue abierta; no se declara validación de micrófono humano, precisión ni autorización de distribución.
