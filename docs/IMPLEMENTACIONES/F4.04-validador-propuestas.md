## Uso y resultado tipado

`InformationProposalValidator.validate(request, document)` se invoca **explícitamente** después de `InformationExtractor`. El extractor y su fake conservan su responsabilidad de producir documentos no validados y su modo SYNTHETIC_FIXTURE/MODEL_OUTPUT; la validación no transforma un fake en IA real. Los fallos de extracción siguen fuera de este contrato.

```kotlin
// Ejecutar esta fase acotada en un worker; no se conecta aún con UI ni persistencia.
when (val extracted = extractor.extract(request)) {
    is InformationExtractionResult.Proposals -> validator.validate(request, extracted.document)
    is InformationExtractionResult.NoProposals -> validator.validate(request, extracted.document)
    is InformationExtractionResult.Failure -> { /* manejar el error del extractor */ }
}
```

- `Valid(document, reviewRequirements)`: JSON exacto sin mutaciones, outcome y número de propuestas. `requiresHumanReview` siempre es true. El protocolo conserva PROPOSED/UNVALIDATED; incluso NO_PROPOSALS es un resultado distinto de fallo.
- `Rejected(error)`: primer error determinista, con enum de código, ruta estructural tipo JSON Pointer y posición de carácter cuando corresponde al parser. No se devuelven citas, nombres, valores, claves adicionales desconocidas ni excepciones del proveedor.
- `validateJson` permite validar directamente un String; `validateUtf8` comprueba bytes antes de decodificar, sin reemplazo silencioso de secuencias inválidas. La entrada F4.03 verifica además que outcome/versión del wrapper coincidan con el JSON realmente comprobado.

El documento comprobado no es una entidad Room ni un DTO aceptado de Agenda. No tiene funciones para guardar, confirmar rutinas, programar alarmas, actualizar hechos, enviar mensajes o abrir URLs. No hay logs de payloads. El host futuro mantendrá la procedencia del extractor junto a este resultado y aplicará revisión/consentimiento por separado.

## Una definición estructural, sin dependencias nuevas

El archivo normativo sigue siendo `docs/CONTRATOS/IA/v1/proposals.schema.json`, dialecto 2020-12, versión 1.0.0, SHA-256:

`724680a219eade0de966a8ae33bf79531c5b7b3d440c4a21921055703f45d8a5`

Gradle copia solo ese archivo al directorio generado propio de build y lo empaqueta como `/proposals.schema.json`. No hay segunda copia versionada, DTOs paralelos de las once variantes, ni schema reescrito a mano en Kotlin. Ambos APK se inspeccionan para comprobar bytes/hash y ausencia de `fixtures/`.

Se implementa un evaluador **limitado al vocabulario de ese artefacto fijado**, no un SDK general de JSON Schema: `$ref` local a `$defs`, type/const/enum, properties/required/additionalProperties/minProperties/dependentRequired, items/minItems/maxItems/uniqueItems, longitudes Unicode, pattern, formato date, minimum/maximum y allOf/anyOf/oneOf/if/then/not. Comprueba vocabulario, referencias locales y hash al cargar. Un recurso ausente/alterado se rechaza como SCHEMA_CONFIGURATION; no se consulta ninguna URL ni se adapta una versión desconocida. Añadir un nuevo schema/vocabulario exige implementación y pruebas explícitas futuras.

Justificación: no existe parser de producción independiente de Android en el proyecto; org.json de Android no serviría como contrato JVM autónomo y un motor genérico de schema introduciría dependencias adicionales. El pequeño árbol sintáctico interno no define otra taxonomía. El coste de mantener/auditar este parser y evaluador es una limitación real: los casos actuales no certifican conformidad universal con todos los dialectos/keywords de JSON Schema. D-016 registra esta decisión, sin modificar D-015.

## Límites antes y durante el procesamiento

| Límite | Aplicación |
|---|---|
| 262.144 bytes UTF-8 | Antes de decodificar ByteArray; en String se cuenta UTF-8 sin crear primero otra copia grande. Exactamente el límite sigue permitido. |
| Profundidad 32 | Se detiene el descenso del parser, antes de construir árboles arbitrariamente profundos. |
| 24.000 nodos | Presupuesto de sintaxis independiente del tamaño en bytes. |
| Números | Hasta 128 caracteres y escala decimal entre -1.000 y 1.000; BigDecimal, sin NaN/Infinity o redondeos Double. |
| 300.000 pasos de schema | Cota adicional para evaluación de ramas/combinadores; fail closed con PROCESSING_LIMIT. |
| 1.024 evidencias totales | Además del máximo por campo; se detiene el cotejo al excederlo. |
| Presupuestos de protocolo | 16 fuentes, 32 propuestas, 16 incidencias, longitudes y cotas de cada variante, sin ampliar listas. |
| Petición del host | Se reutilizan las ventanas/longitudes inmutables F4.03: hasta 32.768 unidades UTF-16 autorizadas en total. |

Se rechazan claves duplicadas incluso mediante escapes equivalentes, BOM, comentarios, datos alrededor/trailing commas, controles sin escape, UTF-8 inválido y sustitutos Unicode aislados tanto literales como escapados. Sin coerción de números/strings. Long decimal de épocas/correctionId se coteja exactamente; no se reinterpretan milisegundos. Los IDs locales se cotejan completos, sin aceptar un salto de línea final por diferencias entre motores regex.

Los presupuestos de trabajo son límites de seguridad adicionales del host: un documento artificial que formalmente pase schema puede excederlos y ser rechazado. No se recorta una respuesta para hacerla pasar ni se cambia el original. No hay expansión de calendarios o evaluación de código contenido en citas.

## Evidencia, fuentes y grafo

1. Correlación exacta requestId/extractionId/versión. El eco de snapshots debe cubrir las revisiones autorizadas exactamente una vez y coincidir en ID, revisión, origen, captura, zona, hash, longitud y ventanas. El hash no da permiso por sí solo.
2. Cada evidencia/ancla debe usar una fuente de la solicitud y la revisión exacta. Dos revisiones del mismo ID no se convierten en observaciones independientes.
3. Rangos absolutos UTF-16 `[inicio, fin)`, ordenados y contenidos íntegramente en una ventana autorizada. No se cortan pares sustitutos. Se coteja substring literal sin normalización, incluyendo emoji y CRLF; no se busca otra aparición para reparar offsets.
4. Todos los campos y las evidencias de incidencias se recorren. Una cita adicional falsa invalida el documento aunque las otras sean correctas.
5. IDs de propuesta únicos y de ocurrencia/excepción únicos dentro de su propietario. Referencias forward válidas si resuelven; destinos ausentes, autorreferencias, tipos incompatibles y ciclos de dependsOn/UPDATES se rechazan. CONTRADICTS no se resuelve automáticamente ni exige un grafo acíclico de contradicciones.
6. Tipos de actor/person/participants/speaker, proyecto, objetivo, dependencias, progreso, sujeto, ocurrencia enlazada y objetivo de recordatorio siguen F4.02. UPDATES/CONTRADICTS conservan categoría compatible; `issues.affectedProposalIds` también se comprueba. BEFORE debe corresponder al tipo del objetivo, por ejemplo EVENT_START no puede señalar TASK.

No se fusionan personas/proyectos por título, no se deduplican extracciones semánticamente y no se verifica identidad real. F4.09 abordará ese problema separado.

## Reglas semánticas comprobables y frontera humana

- El alcance negado del título no puede presentarse como actividad afirmada activa/completada. Un título hipotético no permite elevar un estado a ASSERTED. Un relato de finalización que conserva incertidumbre tanto en título como estado puede seguir como **propuesta incierta**; no se rechaza solo por ser incierto.
- Reglas deliberadamente estrechas detectan los ejemplos «Ya terminé el informe» con estado pendiente y «Cancelé la reunión/la cita/la tarea» con estado activo; también «No tengo reunión…» despojado de negación y «Quizá/Tal vez/Puede que…» promovido a afirmación en cláusulas simples. Se comprueba la cita de state, no solo el título que puede citar únicamente «el informe». Las reglas léxicas evitan conjunciones adversativas/coordinadas y no se extrapolan a «terminé la primera parte del informe» o «cancelé la cancelación»: completar un paso no completa todo el trabajo. Un test conserva ese caso legítimo pendiente de revisión.
- No es un clasificador lingüístico general. Cambios de sujeto, ironía, frases compuestas, modalidades, intención y significado requieren revisión. Un fragmento auténtico no demuestra por sí solo que el valor esté sustentado; por ello todos los resultados conservan HUMAN_MEANING_REVIEW y LINGUISTIC_SUPPORT_UNDECIDED. No se presenta una cita correcta como un detector infalible de alucinaciones.
- OBSERVED respeta las exigencias estructurales de periodo, ocurrencias, base inferida y evidencias. Se exige independencia mínima por ID de fuente y al menos dos fuentes de ocurrencias, sin contar revisiones/repeticiones del mismo recuerdo como fuentes distintas. Conserva OBSERVED_PATTERN y revisión; no impone una probabilidad de regularidad ni transforma clasificación ASSERTED en aceptación del usuario.
- HABIT conserva frecuencia deseada separada de rutina observada/evento recurrente. La estructura no prueba que el modelo eligió bien la categoría: el significado de esa elección se revisa, sin derivar intención de observaciones o ausencia de notas. SKIPPED_EXPLICITLY no admite una base inferida por falta de registros.
- Conclusión personal acotada: fuentes independientes, periodo/contexto y condiciones del schema; descripción de personalidad no puede convertirse en un perfil inferido por MODEL_CONCLUSION. Opiniones y preferencias conservan atribución y PERSONAL_CLAIM; no se verifica que un tercero realmente sea así ni se infiere un diagnóstico.
- REMINDER exige petición con base EXPLICIT, ASSERTED y AFFIRMED; una fecha/día solo no sirve de petición. Un wording no reconocido no se declara semánticamente demostrado: requiere revisión. No se genera ninguna acción o autorización de notificación.
- `technicalScore` permitido por schema se conserva solo como diagnóstico **no confiable**, con TECHNICAL_SCORE_NOT_TRUSTED: no se usa para aceptar afirmaciones, ordenar prioridades ni activar acciones. No se conoce aquí un catálogo verificable de métodos. No se inventan porcentajes/calibración y el editor no se modifica.

## Temporalidad y recurrencia sin adelantar F4.05

- Validación de fechas Gregorianas reales y horas, Long exacto, zona conocida por las reglas TZDB disponibles del runtime, excluyendo alias Java que no son IANA. Se conservan aliases IANA reales como CET/EST, no solo nombres que contienen `/`. Una zona desconocida no cae silenciosamente en GMT.
- El ancla debe pertenecer a las fuentes de la expresión. `resolved=null` sigue intacto para fechas relativas/ambiguas. Una resolución autocoherente tampoco demuestra que sea la ocurrencia correcta; literales fecha/hora/zona distintos de su evidencia se rechazan cuando son comparables y resoluciones lingüísticas se señalan para F4.05.
- Si hay instante, se exige equivalencia con fecha/hora/zona suministradas. Se comprueba precisión/consistencia, no se inventa medianoche. Se detectan huecos DST; solapamientos quedan indicados para revisión temporal, sin escoger una hora nueva. No se calculan «mañana», «el viernes» o fechas de hechos a partir de captura.
- Se comprueba orden de periodos/inicio-fin y pertenencia de ocurrencias/excepciones cuando sus componentes ya resueltos son comparables. Si faltan extremos/resoluciones o las zonas no permiten comparación inequívoca, no se inventa el orden.
- Recurrencia: combinaciones permitidas por schema, unicidad semántica por valor (10:00 y 10:00:00 son duplicadas), meses/días imposibles, ocurrencias resueltas frente a día de semana sin excepción declarada. Días 29–31 o calendarios incompletos mantienen revisión: no se genera una política de omisión/traslado ni se concluye incumplimiento.

Las comprobaciones de calendario usan java.util/GregorianCalendar/TimeZone disponibles en minSdk 24, sin java.time no desugared ni dependencias nuevas. Su dataset de zonas depende del dispositivo/JVM. Se prueban DST de Nueva York y años bisiestos en JVM, **no se certifica aquí ejecución física en API 24**. F4.05 deberá tratar resolución lingüística, conflictos de evidencia temporal, políticas de recurrencia y casos de zonas con sus límites explícitos.

## Riesgos y handoff F4.05

F4.04 queda implementada para su alcance con límites humanos/temporales explícitos. Una validación satisfactoria permite revisar propuestas, **no confirma su semántica completa ni programa nada**. No se resuelven entidades/duplicados de dominio, veracidad de opiniones, sentido de frases arbitrarias, consentimientos cloud o autenticidad externa de las fuentes.

Handoff preparado exclusivamente para F4.05: resolver referencias temporales sobre las fuentes/versiones/ventanas autorizadas, conservando expression/anchor, detectar ambigüedad y volver a comprobar evidencia/consistencia sin usar captura como ocurrencia. No se inicia esa tarea ni F4.06–F4.17.

Permanecen pendientes F3.06/distribución/procedencia/licencias/ELF-RELRO16KB, TTS audible offline formal, origen mixto TEXT/VOICE y revisión dinámica/mapa opcional solo con incertidumbre calibrada. La futura IA cloud interpreta únicamente texto consentido por envío, conserva original local inmutable y devuelve resultados estructurados revisables con evidencia; no se transmite audio ni notas en este ticket.
