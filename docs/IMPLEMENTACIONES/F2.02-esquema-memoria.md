# F2.02 — Esquema mínimo de memoria v1

## Alcance

Define el esquema físico inicial para conservar la captura original y dejar preparada su evolución. No se crearon en el proyecto entidades, DAO, base de datos, migraciones, repositorio ni conexiones desde UI. F2.03/F2.04 implementarán los tipos Room definitivos.

## Tabla `memory_entries`

Todos los campos son obligatorios (`NOT NULL`); el contrato Kotlin ya rechaza valores vacíos para `id`, `rawText` y `timezoneId`.

| Columna | SQLite | Kotlin / contrato | Decisión |
|---|---|---|---|
| `id` | `TEXT NOT NULL PRIMARY KEY` | `MemoryEntry.id: String` | ID estable asignado al convertir `CaptureInput` en entrada; no autogenerado por SQLite. PK aplica unicidad e índice de búsqueda. |
| `rawText` | `TEXT NOT NULL` | `CaptureInput.rawText` / `MemoryEntry.rawText: String` | Texto original literal; no recortar, normalizar ni reemplazar por texto derivado. |
| `sourceType` | `TEXT NOT NULL` | `CaptureSourceType` | Valores v1 `TEXT` y `VOICE`, almacenados por nombre (`name()`), no ordinal. Room 3 incorpora conversión enum→nombre; renombrar un valor requerirá migración. |
| `capturedAtEpochMillis` | `INTEGER NOT NULL` | `Long` | Instante UTC en milisegundos Unix, como F1.01. No guardar fecha local duplicada. |
| `timezoneId` | `TEXT NOT NULL` | `String` | ID IANA de la zona al capturar. La validez semántica se comprueba antes de insertar; SQLite solo asegura tipo/no nulo. |

SQL v1 esperado, contrastado con el esquema Room generado en el spike aislado:

```sql
CREATE TABLE IF NOT EXISTS `memory_entries` (
  `id` TEXT NOT NULL,
  `rawText` TEXT NOT NULL,
  `capturedAtEpochMillis` INTEGER NOT NULL,
  `timezoneId` TEXT NOT NULL,
  `sourceType` TEXT NOT NULL,
  PRIMARY KEY(`id`)
);
CREATE INDEX IF NOT EXISTS `index_memory_entries_capturedAtEpochMillis`
  ON `memory_entries` (`capturedAtEpochMillis`);
```

El orden de las columnas físicas lo determina la declaración Entity; no cambia el contrato. La consulta temporal será `ORDER BY capturedAtEpochMillis DESC, id DESC`: las entradas más recientes primero y el ID como desempate determinista cuando dos capturas compartan milisegundo. El índice secundario no único cubre rangos y orden temporal (SQLite puede recorrerlo al revés). No se añade índice por origen sin un caso de consulta que lo justifique.

## Contratos y estado

- `CaptureInput` no contiene ID: la capa que crea la entrada asigna un `String` estable y persiste los otros cuatro valores sin transformación. `MemoryEntry` se reconstruye desde esa fila.
- No persistir `CaptureStatus`: `IDLE`, `SAVING` y `FAILED` describen estados de la solicitud/UI; una fila existente implica `SAVED`, que el mapper asignará al reconstruir `MemoryEntry`. Las fixtures demo conservan `IDLE` y no se insertan en esta tabla.
- No incluir `title`, resumen, fecha/local-day, `eventAt`, extracción, `createdAt` duplicado, flags de revisión o columnas de UI. Se derivan al leer o pertenecen a fases posteriores.
- El ID y texto no vacíos dependen también de las invariantes de dominio F1.01. La zona debe ser un ID IANA válido; F1.01 solo valida que no esté vacía, por lo que el caso de entrada inválida queda para la capa que construya/persista la captura, sin ampliar aquí el contrato.

## Room 3, KSP2 y exportación

- La API es Room 3.0.3 (`androidx.room3`), compilador Kotlin por KSP2 2.3.12. La prueba aislada confirmó que `String`/enum generan `TEXT`, `Long` genera `INTEGER`, los campos no anulables generan `NOT NULL`, la PK string no se autogenera y el índice temporal se exporta.
- Al crear la base definitiva, aplicar el Room Gradle Plugin `androidx.room3` 3.0.3 y configurar `room3 { schemaDirectory("$projectDir/schemas") }`. El plugin organiza y copia snapshots JSON versionados por clase de base y versión; guardar `app/schemas/**` en control de versiones. No fijar opciones de variantes que el proyecto aún no tiene.
- Versión inicial de `@Database`: `1`. Cada cambio de forma incrementará la versión y conservará el JSON previo. No habilitar destructive fallback ni borrar snapshots.
- Room 3 usa migraciones/callbacks con `SQLiteConnection`; cambios simples y no ambiguos pueden usar auto-migration con snapshots. Renombres/eliminaciones ambiguos requieren spec; transformaciones de contenido requieren migración manual. No se implementaron migraciones en F2.02.
- En F2.12, `room3-testing`/`MigrationTestHelper` debe abrir snapshots anteriores y validar schema y conservación de filas/valores. Añadir pruebas DAO/in-memory al implementar F2.03/F2.04; no se ejecutaron tests de aplicación en este ticket.

## Validación aislada

Se creó un proyecto temporal fuera del repositorio (sin agregar ni cambiar dependencias del proyecto) con AGP 9.4.1, Gradle Wrapper 9.6.0, el plugin Compose Kotlin 2.2.10 que usa el proyecto, KSP 2.3.12/KSP2, Room 3.0.3, compile/target SDK 37, min SDK 24, JDK 25 para Gradle y source/target Java 11. El spike temporal declaró una tabla de prueba, enum de origen, DAO de lectura ordenada y base v1 únicamente para activar el procesador y el exportador.

- `:app:kspDebugKotlin` y `:app:copyRoomSchemas` → `BUILD SUCCESSFUL`; JSON generado en `app/schemas/com.yezvi.probe.ProbeDatabase/1.json` con las afinidades, nullability, PK e índice esperados.
- `:app:compileDebugKotlin` → `BUILD SUCCESSFUL`; la implementación Room generada compiló con la misma configuración de SDK/JDK/bytecode.
- El schema es evidencia del spike, **no** el schema de YEZVI: no se copió porque su paquete/clase de prueba no es la base definitiva. La exportación real de `app/schemas` queda pendiente de F2.04, cuando exista la declaración `@Database` definitiva.

La prueba inicial del entorno temporal no encontró `ANDROID_HOME`; al pasar explícitamente el SDK local, tanto procesamiento como compilación pasaron. No hubo cambios de producción ni hace falta repetir esta validación salvo cambios en plugins/versiones.
