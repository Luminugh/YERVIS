### Política de fuente y borrado

Antes de una escritura, la capa DAO revalida dentro de la transacción la existencia y revisión vigente de cada fuente, `sourceType`, captura UTC/zona, longitud UTF-16 y hash del texto original o corrección. La capa de dominio/validador también conserva y compara cita, offsets y ventanas autorizadas. Una propuesta de varias fuentes queda ligada a todas ellas.

Al borrar un recuerdo individual o una selección, `MemoryEntryDao` borra primero, en la misma transacción, **todas las propuestas del extractionId que dependan de cualquier recuerdo seleccionado**; elimina así payloads, versiones, evidencias, vínculos dentro del payload y decisiones. Luego borra los recuerdos; las correcciones heredadas se eliminan con su FK CASCADE. La FK de fuente usa RESTRICT como defensa en profundidad: un borrado que no pase por la operación transaccional no puede dejar derivados huérfanos. Si falla el borrado del recuerdo, Room revierte también la eliminación de derivados.

### Frontera de confianza y operaciones

`RoomInformationProposalRepository` revalida con el validador F4.04 y el resolutor F4.05 antes de persistir. La salida del extractor se almacena como propuesta PROPOSED; guardar una propuesta no la confirma. Confirmar/rechazar requiere acción explícita y escribe la transición devuelta por `ProposalLifecycle`, el ID de acción, la versión exacta y la proyección en una transacción. Reintentos equivalentes son idempotentes; una reutilización incompatible de `actionId` o versión obsoleta se rechaza.

Una edición de usuario permitida mientras la propuesta sigue PROPOSED crea una versión USER nueva; no modifica el payload anterior, `rawText`, capturas ni correcciones. La edición debe pasar F4.04/F4.05 y solo una acción posterior puede confirmarla. No se convierten estados de propuesta en estados de actividad ni en ocurrencias realizadas. `find()` verifica hashes, fuentes, schema/evidencia y reproduce la secuencia persistida mediante F4.06; una cadena imposible no se presenta como confirmada.

## Rollback, límites y riesgos

SQLite ejecuta la migración como transacción; una falla comprobada conserva v2 y sus filas. No existe downgrade automático v3→v2. Si un despliegue futuro necesitara volver a una versión antigua, debe publicar una versión compatible con v3 o restaurar de manera controlada una copia completa de DB+WAL/SHM; nunca usar migración destructiva. La autorización actual no cubre ese paso físico.

Cada propuesta conserva el documento JSON completo para poder validar relaciones cruzadas y reconstruir el conjunto; por lo tanto, varias versiones por propuesta duplican bytes y consumo en DB. Los límites de entrada F4.04 (262.144 bytes) acotan cada payload, pero el multiplicador por propuestas/versiones es un costo conocido. El borrado transaccional elimina el conjunto entero para evitar retener datos derivados de una fuente borrada.
