# F2.13 — Estrategia de esquemas y migraciones

## Auditoría de Room v2

`YezviDatabase` declara versión 2, ambas entidades y `exportSchema = true`. El snapshot v1 describe `memory_entries` con ID y texto originales, instante UTC en milisegundos, zona IANA y origen, todo `NOT NULL`, además del índice por instante. El snapshot v2 conserva esa tabla y agrega `memory_entry_corrections`, con PK autogenerada, FK a `memory_entries.id` con `ON DELETE CASCADE` e índice `(memoryEntryId, correctionId)`. Los campos, tipos, nullability, claves e índices de ambos JSON coinciden con las entidades actuales y con la migración 1→2.

`1.json` está seguido por Git y coincide con HEAD, sin modificación accidental. `2.json` estaba generado en `app/schemas` pero sin seguimiento; se añadió al índice de Git para incluir el snapshot en el próximo checkpoint. Su contenido no se editó. Sigue sin commit, conforme al alcance de F2.13.

`YezviDatabaseFactory` registra explícitamente `MIGRATION_1_2`; `rg` no encontró `fallbackToDestructiveMigration` en código de producción ni configuración Gradle. La migración es aditiva: crea tabla e índice, sin mutar ni copiar recuerdos existentes.

## Cobertura y límites del workaround

`MemoryCorrectionMigrationTest` usa SQLite de archivo con el DDL, índice, `user_version` e `identityHash` tomados del snapshot v1. Inserta un recuerdo sintético con todos sus metadatos, lo abre con la factory de producción y deja que Room valide el schema de destino. La igualdad de la entidad comprueba la preservación exacta; las correcciones prueban append-only, la FK rechaza un padre inexistente y el cierre/reapertura verifica persistencia. Al abrir v2, la validación de Room cubre columnas, índices y relaciones declarados; F2.12 prueba además cascada y ausencia de huérfanos en SQLite.

El caso de error induce un conflicto sintético al crear el índice. Comprueba que el upgrade falla sin cambiar `user_version`, perder el recuerdo ni dejar la tabla parcial. Es una validación del rollback transaccional, no una simulación exhaustiva de fallos de almacenamiento físico.

No se usa `MigrationTestHelper`: la investigación F2.09 registró que Room 3.0.3 requiere kotlinx.serialization 1.8.1 para leer snapshots, mientras la resolución consistente actual fija 1.7.3; el helper falló con `AbstractMethodError` antes de ejecutar la migración. La prueba conserva SQLite real y ejercita la factory, el driver, el registro de la migración y la validación de Room; evita agregar o forzar dependencias solo para el helper. Limitación: el DDL y el hash v1 están duplicados en el fixture de prueba. Deben cotejarse con el snapshot inmutable cuando se revise esa prueba; no representan una fuente alternativa para cambiar v1.

## Procedimiento para futuras versiones

1. Antes de cambiar `@Database.version`, conservar cada `N.json` ya publicado sin sobrescribirlo. Generar `N+1.json` con Room/KSP, revisar el diff de tablas, columnas, tipos, nullability, índices, claves y acciones FK, y comprobar que el snapshot anterior permanece idéntico. Mantener los snapshots bajo Git y confirmarlos junto con la migración correspondiente.
2. Crear una migración explícita `N→N+1`, registrarla en `YezviDatabaseFactory` y evitar fallback destructivo. Para upgrades desde más de una versión soportada, probar cada origen y su cadena de migraciones hasta la versión actual.
3. Mantener archivos fixture de SQLite por versión con datos exclusivamente sintéticos e inmutables. Cada ejecución migra una copia; no altera el snapshot de origen. Verificar conservación de IDs, texto original y metadatos, índices, claves/acciones FK, consultas DAO y reapertura con Room nuevo.
4. Incluir un caso de fallo de migración y comprobar que la transacción deja intactos el archivo de origen, su `user_version` y sus datos, sin tablas parciales. Corregir y reintentar sobre otra copia; nunca borrar o reemplazar la base fallida automáticamente.
5. Si `MigrationTestHelper` pasa a ser compatible con las versiones resueltas, podrá reemplazar o complementar el fixture manual. Mientras tanto, cotejar su DDL/hash con el JSON de origen y abrir siempre la base migrada con la factory/Room reales.
6. La política de backup de producción sigue pendiente en D-011. Esta estrategia exige conservar snapshots de schema y fixtures de prueba, pero no afirma que la app haga backups del archivo de usuario. Antes de distribuir una actualización con migración, definir y validar por separado una vía de backup/restore compatible con privacidad; ante fallo de migración, conservar el archivo y no ofrecer una base vacía como recuperación.

## Resultado y handoff

No se cambió código, entidades, schemas ni migraciones y no se ejecutó Gradle. No apareció una nueva decisión que requiera ADR. F2.13 queda documentada. Siguiente tarea: F2.14 — prueba integral offline; no iniciada. No avanzar automáticamente.
