# F2.04 — Base de datos Room y driver SQLite

## Alcance

Se creó la base SQLite local v1 y su inicialización mínima. La base registra `MemoryEntryEntity` y `MemoryEntryDao` de F2.03. No se conectó UI, no se implementó repositorio/ViewModel ni se añadieron migraciones o fallback destructivo.

## Base y factory

`YezviDatabase` está anotada con `@Database(entities = [MemoryEntryEntity::class], version = 1, exportSchema = true)` y expone el DAO. El Room Gradle Plugin `androidx.room3` 3.0.3 configura `app/schemas` como salida de snapshots. KSP2 2.3.12 generó `YezviDatabase_Impl` y `MemoryEntryDao_Impl`.

`YezviDatabaseFactory.getInstance(context)` crea una instancia compartida con doble comprobación sincronizada y `@Volatile`; el builder usa `context.applicationContext` y nombre estable `yezvi.db`, así no retiene una Activity. Un punto interno de creación con nombre permite que instrumentación use un archivo temporal independiente sin alterar la instancia de producción ni depender de DI.

## Driver elegido

Se usa `AndroidSQLiteDriver` de `androidx.sqlite:sqlite-framework:2.7.1`, sobre las APIs `android.database.sqlite` del sistema. El proyecto tiene `minSdk 24`; la dependencia es Android y la compilación/manifest merge con ese minSdk pasó. Se eligió sobre `BundledSQLiteDriver` porque YEZVI es Android-only y el driver de plataforma evita empaquetar y actualizar binarios SQLite nativos adicionales. La consecuencia es que la versión del motor puede variar entre versiones del sistema; la prueba instrumentada corrió en API 37. [AndroidSQLiteDriver API](https://developer.android.com/reference/kotlin/androidx/sqlite/driver/AndroidSQLiteDriver) · [SQLite releases](https://developer.android.com/jetpack/androidx/releases/sqlite).

El builder Room usa `Room.databaseBuilder<YezviDatabase>(context.applicationContext, databaseName).setDriver(AndroidSQLiteDriver()).build()`. No llama `allowMainThreadQueries`, no habilita `fallbackToDestructiveMigration` ni elimina bases por error.

## Schema v1

Room produjo y se versionó en Git `app/schemas/com.yezvi.assistant.data.local.memory.YezviDatabase/1.json`. Su definición corresponde al contrato F2.02:

| Columna | Afinidad | Nullable | Clave/índice |
|---|---|---|---|
| `id` | `TEXT` | No | PK; no autogenerada |
| `rawText` | `TEXT` | No | Texto original |
| `capturedAtEpochMillis` | `INTEGER` | No | Índice no único |
| `timezoneId` | `TEXT` | No | ID IANA |
| `sourceType` | `TEXT` | No | `TEXT` o `VOICE` por nombre |

La consulta mantiene `ORDER BY capturedAtEpochMillis DESC, id DESC`. La comparación del JSON generado verificó versión 1, tabla, cinco columnas/afinidades/nullability, PK, índice y SQL de creación contra F2.02. No incluye datos, estados de captura ni columnas derivadas.

## Prueba SQLite real

`YezviDatabaseTest` corre en Android instrumentado con `AndroidSQLiteDriver` y un nombre de base temporal. Solo inserta cadenas sintéticas. Verifica inserción de dos filas, búsqueda por ID, `Flow` ordenado y desempate descendente por ID al compartir instante, actualización de zona, cierre de la conexión Room, reapertura del mismo archivo y lectura de los valores conservados, borrado y ausencia posterior. En `finally` cierra y elimina el archivo de prueba.
