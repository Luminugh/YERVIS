# F2.11 — UI de edición, borrado y errores

## Resultado

Detalle permite corregir el texto vigente con una escritura explícita al `MemoryCorrectionRepository` existente. Cada guardado confirmado agrega una revisión; `MemoryEntry.rawText` se sigue leyendo y mostrando como original. La pantalla diferencia original, versión vigente e historial, ordenado por `correctionId` ascendente y fechado en la zona horaria guardada.

La edición permanece en Detalle. Cancelar o volver mientras se edita descarta solo el borrador local y no llama al repositorio. Durante el guardado se bloquean edición, cancelación y navegación; el error conserva el borrador para reintentar, y el mensaje de éxito aparece solo después de que `addCorrection` devuelve la revisión persistida. Las cancelaciones de corrutina siguen propagándose.

Se conserva el único diálogo de borrado de F2.10: cancelar no escribe, la confirmación invoca el borrado ya existente, los botones quedan bloqueados durante la operación y el diálogo de éxito aparece únicamente al recibir `EntryDeleteUiState.Deleted`. La cascada y el schema v2 no se modificaron.

## Accesibilidad y comportamiento

- Editor multilínea con capitalización de frases, acción IME Done, ajuste al teclado y botones de guardar/cancelar con objetivo mínimo de 48 dp.
- Encabezados semánticos para versión vigente, original, historial y metadatos; el editor y las acciones tienen etiquetas visibles y tags de prueba.
- Atrás cancela la edición pendiente antes de abandonar Detalle. Mientras se escribe en SQLite, navegación y cancelación quedan temporalmente bloqueadas.
- No se añadieron dependencias ni se cambió el contrato de dominio, las pantallas Hoy/Capturar/Memoria, DAO, esquema o migraciones.

## Validación

La prueba unitaria `EntryDetailViewModelTest` cubre inserción de una revisión, conservación del original, timestamp, estados, doble toque, cancelación, fallo/reintento con borrador y cancelación de corrutina. La instrumentada `EntryDetailEditingTest` usa un archivo SQLite temporal y datos sintéticos para probar cancelación, error SQL inducido, reintento, historial/versiones, borrado confirmado y reapertura. `EntryDetailAndAccessibilityTest` conserva pruebas de diálogo y targets UI.

`:app:assembleDebug` y `:app:testDebugUnitTest` → `BUILD SUCCESSFUL` (26/26 unitarias). `:app:compileDebugAndroidTestKotlin` también pasó. La suite conectada completa ejecutó 22 casos y reportó 2 fallos: una aserción de la prueba nueva usó `assertTextEquals` para `EditableText` y ya fue corregida; `MemoryPersistenceTest.emptyTimelineUpdatesFromCaptureAndSurvivesActivityRecreation` tuvo un timeout de Compose/Espresso en su línea 91. Tras corregir el matcher, `EntryDetailEditingTest` focalizado pasó 1/1 en `Medium_Phone_API_37.0(AVD) - 17` (`emulator-5554`). No se repitió toda la suite porque la prueba F2.11 quedó validada y el timeout restante es de un test preexistente ajeno al alcance.

La ejecución se realizó en AVD API 37; no es validación en Samsung físico. La prueba instrumentada comprueba el flujo visible y la persistencia SQLite con datos sintéticos, sin acceder a la base normal de la aplicación.

## Riesgos y handoff

El historial se consulta al abrir Detalle y se actualiza localmente después del append; `MemoryCorrectionRepository` no expone un `Flow` de correcciones. Un segundo escritor simultáneo no refresca el historial ya visible hasta volver a cargarlo. F2.12 puede cubrir DAO/repositorio y temporalidad sin ampliar el alcance de esta UI.
