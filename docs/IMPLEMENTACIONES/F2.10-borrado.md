# F2.10 — Borrado con confirmación y estado honesto

## Resultado

Detalle ofrece una acción mínima para eliminar un recuerdo real y un diálogo de confirmación. Cancelar o descartar el diálogo no invoca el repositorio. Mientras SQLite procesa el borrado se bloquean confirmaciones repetidas. La pantalla muestra error con opción de reintento si falla; informa éxito únicamente cuando `MemoryRepository.deleteById` confirma que se eliminó una fila. Tras el éxito, un segundo diálogo permite volver a Memoria.

## Integridad y estados

Se mantiene el schema v2 aprobado, sin migración. `memory_entry_corrections.memoryEntryId` referencia `memory_entries.id` mediante `ON DELETE CASCADE`; `MemoryEntryDao.deleteById` ejecuta una única sentencia `DELETE` sobre el padre. SQLite aplica la cascada dentro de la misma sentencia, así que el recuerdo y su historial se confirman o revierten juntos.

`MemoryRepository` y el DAO ahora exponen `observeById`. Memoria ya observa la lista y se actualiza al invalidarse la consulta; Detalle observa el ID y muestra «Entrada no encontrada» si desaparece. Un resultado `false` por carrera tampoco se anuncia como éxito. Las excepciones del almacenamiento llegan al ViewModel, que conserva la pantalla para reintentar; las cancelaciones de corrutina se propagan.

La confirmación explica que la acción no se puede deshacer desde la app. No se promete borrado físico irrecuperable de SQLite ni eliminación de copias de seguridad.

## Pruebas

- Unitarias de `EntryDetailViewModel`: espera del resultado real, doble toque, error con recuerdo visible, reintento y cancelación.
- Instrumentadas de UI: cancelar no llama al borrado; el mensaje de éxito aparece solo al recibir el estado `Deleted`.
- Instrumentadas con SQLite real: eliminación de un recuerdo con dos correcciones, cascada sin huérfanos, emisiones `empty`/`null` de Memoria y Detalle, cierre/reapertura y persistencia del borrado. Un trigger sintético `RAISE(ABORT)` verifica error SQL y conservación del padre e historial.
- `:app:assembleDebug` y `:app:testDebugUnitTest`: `BUILD SUCCESSFUL`; 23 pruebas unitarias sin fallos.
- `:app:connectedDebugAndroidTest`: `BUILD SUCCESSFUL`; 21 pruebas instrumentadas, 0 fallos en Medium Phone API 37 (`emulator-5554`). Incluye cancelación/confirmación UI, cascada/error/reapertura Room, navegación y ciclo de vida de Memoria.
- No se hizo validación visual en un Pixel 8 ni en Samsung físico; la validación instrumentada fue en el AVD API 37.

## Archivos

No se alteraron `YezviDatabase`, entidades, migraciones ni schemas v1/v2; D-011 sigue vigente y no fue necesario registrar un ADR.

## Handoff

F2.10 se limita al borrado y estado mínimo. F2.11 puede diseñar el flujo táctil completo de edición/borrado y sus fallos sin cambiar el contrato de borrado ni el esquema. No avanzar automáticamente.
